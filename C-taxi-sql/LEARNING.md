# 学习指南：纽约出租车行程分析

> 这个项目最值钱的地方不是图表，是**数据质量那一节**。真实数据永远比你想的脏。

---

## 0. 这个项目在干什么

950 万条纽约黄色出租车的真实行程（2024 年 1–3 月），用 SQL 回答：

- 一天里什么时候最忙？一周里哪天最忙？
- 钱怎么付的？小费给多少？
- 哪些区域单量最大？
- 数据有多脏，脏在哪？

---

## 1. 五个必须懂的概念

### ① 数据质量体检：为什么第一件事是数脏数据

打开 `sql/01_quality.sql`，你会看到五个指标：

| 指标 | 含义 | 本次结果 |
|---|---|---|
| `bad_distance` | 里程 ≤ 0 | 21.6 万行 |
| `bad_duration` | 下车时间 ≤ 上车时间 | 2,801 行 |
| `bad_amount` | 总金额 ≤ 0 | 11.7 万行 |
| `missing_zone` | 区域 ID 缺失 | 少量 |
| `out_of_range` | 上车时间不在 1–3 月 | 21 行 |

**为什么要先做这一步？** 因为里程为 0 的行程会把「平均里程」拉低，金额为负的行程会把「总营收」算错。不体检直接分析，结论全是错的。

面试时能说出「我先做了数据质量体检，发现 2.3% 的行程里程为 0」，比背十个算法有用。

### ② 清洗要留痕

看 `sql/02_analysis.sql` 里的 `dim_trip_clean`，过滤条件有四条：

```sql
trip_distance > 0
tpep_dropoff_datetime > tpep_pickup_datetime
total_amount > 0
上车时间在本季度内
时长在 1 分钟到 4 小时之间
```

**最后一条最值得说**：为什么要砍掉 4 小时以上的行程？因为那些是计价器忘关造成的异常，不是真实行程。**每一条过滤都要能给理由**，否则就是"为了让数字好看而删数据"。

### ③ 时间维度：`EXTRACT`

```sql
EXTRACT(hour FROM tpep_pickup_datetime)  -- 0-23
EXTRACT(dow  FROM tpep_pickup_datetime)  -- 0=周日, 6=周六
```

注意 `dow` 是从周日开始的（0 = Sunday），不是周一。这个坑很多人踩。

把它按「星期 × 小时」交叉，就得到热力图的两个轴——这是所有时段分析的标准做法（外卖、打车、商场客流都一样）。

### ④ 占比类指标：窗口函数算分母

```sql
COUNT(*)::DOUBLE / SUM(COUNT(*)) OVER ()
```

`SUM(COUNT(*)) OVER ()` 的意思是：**在不分组的前提下，把各组计数加起来当分母**。这样一行就能同时拿到"本组数量"和"全局总量"。

这是 SQL 里算「占比」最常用的写法，比写两个查询再 join 优雅。

### ⑤ 为什么用 DuckDB 而不是 Excel/pandas

- 950 万行，Excel 直接打不开（上限 104 万行）；
- pandas 能做，但每次都要把数据读进内存，反复按不同维度聚合会很慢；
- DuckDB 是**列式 + 向量化**引擎，直接读 parquet，几秒出结果，而且**语法就是标准 SQL**。

**面试可以这样讲**：「本地做中等规模分析我习惯用 DuckDB，列存 + 直接查 parquet，比 pandas 省内存，比开 Spark 轻。」

2. 打开热力图，找出最忙的格子——**凌晨 2–4 点是不是反而很热？为什么？**（夜生活 + 机场返程）；

## 4. 五个练习

| # | 练习 | 你会学到 |
|---|---|---|
| 1 | 把清洗条件里的 4 小时改成 2 小时，看行数和均价怎么变 | 阈值对结果的敏感性 |
| 2 | 加一张「工作日 vs 周末」的分时曲线 | 用 `CASE WHEN` 造维度 |
| 3 | 算每个区域的「平均小费率」，排序 | 分组聚合 + 比率指标 |
| 4 | 找出行程量最高的 10 天，猜原因 | 从数据到业务解释 |
| 5 | 用 Zone ID 关联官方 zone lookup 表换成地名 | 维表关联（JOIN 的经典场景） |

**第 4 个是面试最爱问的**："你从这个数据里发现了什么有意思的事？"能讲出"3 月某天单量腰斩是因为暴雪"，比背指标强得多。

## 5. 自测题

1. 为什么分析前要先做数据质量体检？
2. `EXTRACT(dow)` 的 0 代表星期几？
3. 为什么要把「时长 > 4 小时」的行程剔掉？
4. 怎么用一条 SQL 同时算「各组数量」和「全局占比」？
5. 950 万行为什么不建议用 Excel 或 pandas？
6. 里程为 0 但金额不为 0 的行程，可能是什么情况？
7. 支付类型 1 和 2 的小费率差很多，为什么？这说明了什么？
8. 你怎么判断某个区域"单量大但质量差"？
9. 如果要算「每小时的平均等待时间」，需要什么数据？
10. 这个分析和"大数据"有什么关系？

<details>
<summary>答案要点</summary>

1. 脏数据会让所有统计量失真，而且越往后越难发现。
2. 周日（Sunday=0，Saturday=6）。
3. 计价器忘关的异常行程，不是真实出行。
4. `COUNT(*) / SUM(COUNT(*)) OVER ()`。
5. Excel 上限 104 万行；pandas 每次聚合都要全量读入内存。
6. 可能是预约单、上车即取消、或计价器故障。
7. 类型 1 是信用卡（可在计价器上直接加小费），类型 2 是现金（无法记录小费）。所以现金小费率 0 不是"不给小费"，是"记录不到"——这是很典型的指标口径陷阱。
8. 看平均金额、平均里程、平均时长，以及小费率；单量大但客单价低的区域可能是短途集散地。
9. 需要行程的"派单时间"和"上车时间"，本数据集只有上/下车时间，所以算不了。
10. 数据量本身是一方面（千万行），更重要的是**处理方式**：列式存储 + 向量化执行 + 只查需要的列，这才是大数据思维在单机上的体现。
</details>

## 6. 面试追问

**Q：这个项目你最大的发现是什么？**
> 两个。一是数据脏得超出预期，2.3% 的行程里程为 0，不做体检算出来的均价是错的；二是现金支付的小费率是 0，但这不是不给小费，是记录不到——指标口径的陷阱。

**Q：为什么不用 Spark？**
> 950 万行单机 DuckDB 几秒就能出结果，上 Spark 的调度和启动开销比计算本身还大。工具要匹配数据量。

**Q：如果数据涨到 100 亿行呢？**
> 分区（按日期）+ 列存（parquet）+ 只查需要的列，再上 Spark/ClickHouse 做分布式。
