# 学习指南：离线数仓分层建模

> 这份文档不是代码说明，是**你要能讲出来**的东西。代码跑通只要五分钟，能讲清楚要两天。

---

## 0. 先搞明白这个项目在干什么

数仓不是「把数据存起来」。数仓解决的是一个管理问题：**同一个指标在不同人嘴里有不同算法**。

财务说上月销售额 100 万，运营说 80 万，是因为一个含退货一个不含。数仓的作用就是把这些口径**固化到代码里**，从此只有一个数。

这个项目做的事情，就是拿一份原始交易数据，走一遍「原始 → 清洗 → 汇总 → 指标」的流水线，让每个数字都有自己的出处。

---

## 1. 五个必须懂的概念

### ① 分层：ODS / DWD / DWS / ADS

| 层 | 全称 | 一句话 | 本项目里的表 |
|---|---|---|---|
| ODS | Operational Data Store | 原始数据原样存，不做任何加工 | `ods_retail` |
| DWD | Data Warehouse Detail | 清洗 + 明细，一行一个事实 | `dwd_order_detail` |
| DWS | Data Warehouse Summary | 按主题预聚合 | `dws_customer` |
| ADS | Application Data Service | 面向业务的口径表 | `ads_kpi_monthly` |

**为什么必须分？**

- 不分层的话，每个报表都要自己写一遍「剔除退货」，写十遍就有十种写法，迟早对不上。
- ODS 不动，意味着**任何时候都能回溯**：发现指标算错了，可以从头重跑，不用求人找原始文件。

**面试怎么问**：「你们数仓怎么分层的？为什么这么分？」
**你不能只背四层名字**，要说出「不分层会怎样」——上面那两条就是答案。

### ② 事实表与维度表（星型模型）

- **事实表**：记录「发生了什么」，有度量值（数量、金额）。本项目的 `dwd_order_detail`。
- **维度表**：记录「谁、什么时候、在哪、什么东西」。本项目的 `dim_customer`、`dim_date`、`dim_product`。

事实表中间，维度表围一圈，形状像星星，所以叫星型模型。

**为什么要拆？** 一个客户改了国家，改维度表一行就行；如果混在事实表里，要改几百万行。

### ③ 粒度（grain）

**这一层一行代表什么？** 这是数仓设计里第一个要回答的问题。

本项目的粒度是：**一个订单里的一行商品**（invoice_no + stock_code）。所以同一个订单会占多行，算「订单数」必须 `COUNT(DISTINCT invoice_no)`，直接 `COUNT(*)` 得到的是行数不是订单数。

**面试陷阱**：「你们订单数怎么算的？」——答 `count(*)` 就露馅了。

### ④ 指标口径

同一个词，算法可能完全不同。本项目在 `sql/04_ads.sql` 里固定了三个：

```sql
复购率   = 下单次数 ≥ 2 的客户数 / 有客户 ID 的客户数
客单价   = GMV / 订单数（订单按 invoice_no 去重）
退货率   = 退货金额 / 正常销售金额
```

**为什么要写死？** 因为「复购率」有人按订单算、有人按客户算、有人算 90 天内。不写清楚，两个部门能吵一天。

### ⑤ 为什么清洗都放在 DWD

看 `sql/02_dwd.sql`，四个过滤条件是：

```sql
quantity > 0        -- 剔除退货单（退货在原始数据里是负数）
unit_price > 0      -- 剔除赠品、内部调拨、价格缺失
customer_id 非空    -- 匿名订单无法归属客户
invoice_no 非空     -- 订单号是粒度键
```

**每一条都要能说出理由**。面试官问「你为什么把退货剔了」，你要答：退货不是销售，混进来会把 GMV 算高；退货数据我在 ADS 层单独算了退货率，没有丢。

## 2. 代码地图

```
A-offline-warehouse/
├── src/run.py               ← 主流程：转换格式 → 按顺序执行 4 个 SQL → 出图 → 生成报告
├── sql/
│   ├── 01_ods.sql           ← 建原始表（只改列名，不动数据）
│   ├── 02_dwd.sql           ← 四个维度表 + 清洗后的事实表  ★重点看
│   ├── 03_dws.sql           ← 客户宽表、商品日汇总
│   └── 04_ads.sql           ← 月度指标、国家排行、全局汇总  ★重点看
└── reports/                 ← 跑完自动生成，别手改
```

**看代码的顺序**：先看 `02_dwd.sql`（理解清洗），再看 `03_dws.sql`（理解聚合），最后 `04_ads.sql`（理解口径）。`01_ods.sql` 五分钟扫一眼就行。

**第 3 步最重要**：改一处，看变化。

你会看到客户数暴涨——因为匿名订单被当成了不同客户。这就是「为什么要清洗」最直观的证明。

## 4. 五个练习（从易到难）

| # | 练习 | 你会学到 |
|---|---|---|
| 1 | 删掉 DWD 里 `customer_id` 非空的过滤，对比客户数 | 清洗规则对结果的影响 |
| 2 | 在 ADS 加一张「新客 vs 老客」月度 GMV 占比表 | 用窗口函数/自关联定义首购 |
| 3 | 把 `dws_customer.aov` 改成 `SUM(amount)/COUNT(*)`，对比差异 | 粒度用错会怎样 |
| 4 | 加一张月度退货率表 | 退货数据在 ODS 不在 DWD，要回源头取 |
| 5 | 给商品加品类维度（需要外部映射表） | 维度建模里最难的部分：维表从哪来 |

**做完第 1、3 个，你对粒度和清洗的理解就够面试用了。**

## 5. 自测题（先自己答，再翻答案）

1. ODS 层为什么不做清洗？
2. `dwd_order_detail` 的一行代表什么？
3. 为什么订单数要用 `COUNT(DISTINCT invoice_no)`？
4. 维度表和事实表各自存什么？
5. 退货单在原始数据里长什么样？为什么不能进 DWD？
6. 复购率和客单价的口径分别是什么？
7. DWS 层存在的意义是什么，直接 DWD → ADS 行不行？
8. 如果老板要「上月新客贡献的 GMV」，你会改哪一层？
9. 数据量涨到 100 亿行，这个设计哪里会先撑不住？
10. 你怎么验证自己算的 GMV 是对的？

<details>
<summary>答案要点（点开）</summary>

1. 保留唯一事实来源，任何指标算错都能从头重跑。
2. 一个订单里的一行商品（订单号 + 商品编号唯一）。
3. 一个订单有多行明细，`COUNT(*)` 数的是行不是订单。
4. 事实表存度量（数量、金额），维度表存描述属性（客户、商品、时间、地区）。
5. 订单号以 `C` 开头、数量为负数。它是退款不是销售，混入会虚高 GMV；单独在 ADS 算退货率。
6. 见 `04_ads.sql` 注释，必须能一字不差说出来。
7. 可以，但每张 ADS 表都要重复算一遍客户聚合，口径容易分叉；DWS 是"算一次，多处用"。
8. DWS 加客户首购时间，ADS 加口径表；不要动 DWD。
9. 全表重跑（`CREATE OR REPLACE TABLE` 全量重建）会先撑不住，需要分区 + 增量。
10. 交叉验证：用一小段明细手工算一遍，和 SQL 结果对；或者用另一个工具（Excel/透视表）算同一批数据。
</details>

## 6. 面试追问（附答题骨架）

**Q：你这个数仓有多少张表？**
> 四层共 9 张：ODS 1 张、DWD 1 张事实 + 3 张维度、DWS 2 张、ADS 3 张。

**Q：为什么 DWS 只做了客户和商品两个主题？**
> 因为 ADS 的指标只用到这两个维度。主题是按下游需求反推的，不是越多越好。

**Q：全量重建还是增量？**
> 现在是全量（数据量小、逻辑简单）。真实生产会按日期分区做增量，并用调度工具串依赖。

**Q：数据倾斜怎么办？**
> 这个数据集里国家维度会倾斜（英国占九成）。可以给热点 key 加随机后缀打散，或者单独处理大客户。

**Q：你怎么保证指标不出错？**
> 口径写在 ADS 层一处，加单测比对固定样本；上游改清洗规则时，跑前后对比。

## 7. 一句话总结

> 这个项目证明的不是「我会写 SQL」，而是「我知道一个指标该在哪一层、按什么粒度、用什么口径算出来，并且能解释每一个数字的来历」。

把这句话练熟，比背十道八股有用。
